# SC132GS 彩色取帧缓冲区审查（2026-11-09）

本次核查覆盖 Sensor.snapshot、RGB888 到 RGB565 原地转换、VICAP 帧归还，
以及 Display / IDE WBC 到 JPEG 编码器的帧生命周期。
结论来自生产源码、SDK 缓存 API 定义、底层映射实现和主机回归测试；
不代表已经在相机上复现或消除了用户看到的紫色横条、局部块状闪动。

## 已修复的缺陷

1. `src/canmv/port/core/mpp_vb_mgmt.c` 使用 cached 映射读取 DMA 产生的帧，
   读取前没有失效缓存。现在在发布帧给 Python 前调用
   `kd_mpi_sys_mmz_invalidate_cache`，失败时不发布图像。
2. RGB565 转换会直接写入该 cached VICAP 帧。旧实现仅解除映射并归还帧，
   没有先清理 CPU 脏缓存。现在在帧仍由调用方持有时执行 flush（清理并失效），
   再解除映射并归还；避免旧的转换结果延迟回写到下一次 DMA 帧。
3. 旧实现解除映射失败后仍归还 VICAP 帧，驱动归还失败后重试又重复解除映射，
   成功后也未清除调用方句柄。现在按实际完成的步骤保留状态，遇到错误停止归还，
   允许重试；成功后清除记录和调用方标记。Sensor 不再忽略释放错误。
4. `src/canmv/port/omv/ide_dbg_vo_wbc.c` 首次编码先取得输入帧 A，
   初始化又取得探测帧 B。Display helper 取得 B 时自动归还 A，
   导致后续提交的 A 已释放。现在先完成初始化，再取得实际编码输入。
5. WBC 编码提交成功后的状态查询失败、取码流超时，旧实现直接归还输入，
   不能证明异步编码器已停止读取。现在走编码器清理路径，停止和销毁通道后
   才归还输入，并清除初始化状态，让下次预览重新初始化。

SDK `src/rtsmart/mpp/userapps/api/mpi_sys_api.h` 明确区分物理内存与 CPU 缓存，
并说明 flush 会清理和失效缓存。普通 cached mmap / munmap 不是帧数据同步屏障。
两个缓冲区结构体补充了结构体标签，以便主机 C++ 测试包含真实 SDK 头文件；
字段布局没有改变。

## 验证

- VICAP 的 9 项 C/C++ 主机测试通过，生产 C 文件直接参与编译；
  包含同一物理帧块连续复用 120 次、缓存失效/清理失败、解除映射失败、
  驱动释放失败与重复释放。
- IDE WBC 的 5 项 C/C++ 主机测试通过，生产编码器文件直接参与编译；
  覆盖初始化探测、连续编码、初始化失败、查询失败和编码超时后恢复。
- Sensor 的 3 项 Python 测试通过，提取并执行生产方法；
  释放失败时保留原帧并阻止新一次 dump。
- 两个生产 C 文件通过 K230 RISC-V 工具链编译；Sensor 模块通过 mpy-cross 编译。
- 非一致性缓存模型下，修改前的 VICAP 实现 9 项测试中 8 项失败；
  原 WBC 实现不能通过首次编码的帧所有权检查。
  这些是主机模型结果，不是实板计数或图像证据。

测试入口见 `src/canmv/unit_test/README.md`。
